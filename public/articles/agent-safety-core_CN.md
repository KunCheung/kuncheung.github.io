# Agent 安全的核心，是约束不确定决策系统

设想一个能访问邮箱、日历、网盘和浏览器的个人助理型 Agent。用户对它说：“帮我把下周去上海出差的事情安排一下。”它会读邮件确认行程，查日历找空档，搜索酒店、调用地图，甚至可能准备下单。

这时，错误未必出现在它的回复里。它可能把网页营销文案当成任务线索，读了不需要读取的私人邮件，或者在预算还没确认时就默认预订。每一步单看似乎都有道理，连在一起却可能把任务带到用户并不想要的结果。

## 一、从回答问题到替用户做决定

过去几年，大模型安全的讨论多半围绕输出展开：会不会被越狱，会不会胡说，会不会泄露隐私。这些确实是核心问题。随着 OpenClaw、Claude Code 和手机系统级智能体进入实际场景，Agent 已经开始读环境、调用工具、执行操作，跨应用替用户完成任务。只检查最后的回答，已经覆盖不了这类系统的风险。

Agent 在执行任务时，会持续理解环境、更新状态，并依据不完整的信息做判断。这些判断经过工具调用，变成数据访问、状态修改，甚至不可逆的操作。开放环境中的信息源混杂，任务链条又长，错误也就有了更多累积和放大的机会。

从这个角度看，几类常见风险其实发生在同一条决策链上。Prompt Injection 是低可信来源越权影响高权限决策；记忆过度召回，是系统访问了本不该使用的信息；工具误调用，把模型的概率性判断直接转成了确定性执行；行为漂移，则让原始目标和限制在长任务中逐渐失效。

Agent 安全因此首先是一个决策系统工程问题。我们要约束的，是一个在开放环境中不断判断和行动、却无法保证始终正确的系统。

## 二、模型之外的确定性锚点

提升模型的判断质量，仍然是必须持续做的工作。理解、推理和任务跟随能力不足，后面的安全设计就会很被动。

这方面已有不少方法：SFT、RLHF、DPO 等后训练方法；Chain-of-Thought、ReAct 和任务分解等推理与提示优化；system prompt、persona、任务模板等角色与语境约束；retrieval、tool use、search 等外部能力；以及运行时的反思和经验反馈。它们都在尝试让模型的行为更稳定、更符合任务预期。

但改善行为分布，还不能替系统规定哪些数据绝不能访问、哪些工具绝不能调用、哪些外部文本绝不能被当作高优先级指令。

比如，一个经过 SFT 和偏好优化的客服 Agent，可能已经能遵循服务话术，在绝大多数工单中正确回复。可一旦它有了退款、改价和查看订单详情的能力，就还需要回答另一组问题：用户描述模糊、上下文混乱或有人恶意引导时，它会不会调用不该调用的能力？执行高风险操作前，条件是否已经满足？语言层面的对齐，并不会自动带来执行层面的硬限制。

模型的不确定性无法被彻底消除，系统就需要在模型判断错误时仍然守住边界。这里把这些不依赖模型临场推断、由系统预先设置的外部支点称为“确定性锚点”：哪些事情不能做，哪些动作必须停止，哪些决定需要额外确认，应当在模型之外有所约束。

工程上，这通常会落实为模型周围的一套 harness。它不替模型思考，而是组织上下文、约束调用、管理状态和权限，在关键节点接入检查、回退与审计。按承担的任务，可以把锚点分成人类锚点和规则锚点。前者处理少量高价值判断，后者承担高频限制和日常兜底。两者都有用，也都可能被误用。

### 人类锚点：把注意力留给关键决定

对于不可逆、代价高或涉及敏感信息的动作，让人最后看一眼，往往有不可替代的作用。但一次点击确认，并不等于一次有效监督。

办公 Agent 每次发邮件、共享文档、修改会议、下载附件都弹出确认框，是一个常见例子。用户起初会认真看，时间一长就可能不读内容，直接点“允许”。频繁确认消耗了注意力，决策疲劳又让人逐渐转向机械同意。流程里还保留着 Human in the Loop，实际监督却已经失效。

人更能承担复杂的价值判断，但注意力、耐心和判断质量都有上限。设计人类锚点时，需要考虑的是在哪些节点请人介入，才能把有限的注意力用在最值得判断的事情上。

### 规则锚点：让日常限制稳定执行

大量高频、稳定、可自动化的限制，更适合交给规则。人会疲劳、分心，设计得当的规则则可以重复执行，不必每次都重新做一次判断。

这里的规则包括权限限制、数据访问控制、工具调用条件、状态转换约束、身份与角色绑定、生命周期限制、任务级最小授权、信息源分层，以及风险分级和审计机制，远不止几条 if-else。它们的作用是限制行动范围，让模型即使判断错了，也不会立刻越界。

还是看旅行预订 Agent。它可以查航班、订酒店、叫车、申请报销，但系统应当预先规定：预算未经确认，不能下单；身份未经验证，不能查看乘机证件信息；未经用户确认，不能跨平台共享行程；任务结束，临时访问权限自动回收。这些限制需要系统执行，不能只指望模型自行克制。

两项具体机制可以说明这一点。

污点追踪（taint tracking）可以给网页、邮件或第三方工具返回的文本标记“低可信来源”。模型试图把带有这类标签的信息传给发邮件、外发文件、支付等高权限执行模块时，引擎中的规则层会拦截这次操作。

临时凭证（ephemeral credentials）则限制权限的范围和有效期。未来更成熟的 Agent 安全架构，很可能会按任务动态签发临时 Token，而不再给模型长期、宽泛的固定权限。例如，Token 只能访问某个日历，只能读不能写，并在任务结束后立即失效。

## 三、用 Prompt Injection 看执行边界

Agent 要完成任务，就得读取外部信息，而这些信息本身并不可信。Prompt Injection 利用的正是这个矛盾。OWASP 也一直将它列为 GenAI 应用的核心风险之一。

系统提示写得足够好、信息来源标得足够清楚，并不意味着模型就能稳定地区分指令和数据。外部文本进入上下文后，会在同一个推理过程中发生语义融合。数据与控制的混淆，在模型架构下很难被彻底消除。

因此，设计防御时需要考虑模型已经受到影响的情况。采用“假设失陷”或“零信任”的原则，关注点就会落到如何阻止后续的实质性破坏上。微软近来的安全建议也强调，应把间接注入、越界调用和高影响误操作作为执行风险，用系统级控制加以约束。

规则锚点在这里有很直接的用途：读取陌生邮件时，不得调用外发工具；临时 Token 只读；任务结束后回收权限。这些限制可以在注入发生后控制影响范围。

还可以进一步按上下文动态降权。Agent 处理陌生网页、外部邮件或第三方文档时，自动移除发邮件、改日历、支付等高风险能力。只有在上下文被清空、任务被重新确认，或者经过人类锚点的强校验后，才恢复权限。

在这种设计下，即使注入成功，模型发出了危险指令，系统层也会拒绝执行。Prompt Injection 说明，模型内部的概率判断会持续受到不可信环境的影响，安全不能主要依靠模型自行辨别指令与数据，必须有模型之外的确定性结构来约束行动。

## 四、接下来需要解决什么

给注入攻击加检测器、给工具调用加黑名单、给记忆访问加过滤器，再多放几个确认框，都有价值。但只按漏洞逐项打补丁，系统容易越来越碎，也难以解释为什么相似问题会反复出现。

需要一起考虑的，是从输入到执行的整条链：模型怎样理解输入，系统怎样区分来源，哪些信息能进入决策，决策怎样变成执行，谁来限制执行范围，以及出错后怎样控制后果、保留审计并纠偏。我更愿意把这件事理解为“治理”，因为它涉及 Agent 整个运行过程的安排。

沿着这个方向，有三个问题值得继续做。

第一，怎样把人工确认积累成可复用的偏好和规则？除了避免机械点击，还要让一次有效判断能够帮助后续任务，而不必每次都重新询问。

第二，怎样建立跨信息源的信任与权限模型？system、user、网页、文档、邮件、工具返回值，形式上都是文本，可信等级和控制权限却不同。需要建模的是输入侧的信任和权限，覆盖的范围也比单纯防御 Prompt Injection 更大。

第三，怎样让安全机制覆盖长链任务？多步计划、状态更新和工具调用会让风险一路累积、放大，静态防御难以覆盖整个过程。任务推进时，约束也需要持续有效。

这些问题指向同一个目标：承认模型会犯错，同时让系统整体保持可靠。信息源分层、最小权限、人或规则对高风险动作的介入，以及对错误后果的控制，都需要落实到 Agent 的运行过程中。
